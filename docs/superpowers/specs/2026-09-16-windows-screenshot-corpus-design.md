# Windows のスクリーンショットをコーパスにする

作成日: 2026-09-16 (JST)
状態: 2026-09-16に本番反映・運用開始済み。送信・OCR検索・AI生成・MCP・日ビューを検証し、当面は現構成で運用する。

関連: [写真キャプションの検索・エージェント対応](2026-09-14-caption-corpus-design.md)
実装・運用記録: [本番反映と検証結果](../plans/2026-09-16-windows-screenshot-corpus.md)

## 目的

Windows 常駐アプリで PC の画面を記録し、「自分が何を見ていたか」を
検索とエージェントから参照できるコーパスに加える。

## 決定した撮影方針

**画面の変化の有無にかかわらず、常に撮影する。**

2026-09-16 に利用者が指定した方針。撮影タイミングごとにスクリーンショットを取得し、
前回と同じ画面でも撮影を省略しない。撮影間隔は利用者指定の **30秒**。
アプリの設定で変更可能にするが、既定値は30秒とする。

以前の D1 容量対策案「変化がなければ撮らない＋新しい行だけ索引する」は
採用方針ではなく、今回の決定で置き換える。容量対策を理由に変更検知を
撮影条件として導入しない。

「新しい行だけ索引する」を確定要件として扱わない。
以下の詳細設計では保存した全記録のOCR・キャプションを索引し、変更・削除にも追従する。

## アプリの構成

実装場所: `windows/screenshot-agent/`。Python 3.11以降のWindows版を使う。
このPCのARM64版Pythonで実行・検証する。画像取得はPillow、日本語OCRはPyWinRT経由の
`Windows.Media.Ocr`、設定画面はTkinter、タスクトレイはpystray。
ローカルVLMやCUDAは使わない。

| ファイル | 責務 |
| --- | --- |
| `agent.py` | トレイ・設定画面、撮影スケジュール、OCR・送信ワーカー |
| `capture.py` | DPIを考慮した画面列挙と各画面の原寸取得 |
| `ocr.py` | 日本語OCRとJPEGエンコード |
| `store.py` | SQLiteによる永続未送信キュー |
| `transport.py` | 対応確認、multipart送信、応答確認 |
| `config.py` | 設定とDPAPIによる認証情報の保護 |
| `install.ps1` / `launch.vbs` | 依存環境・ショートカット作成 / 起動 |

撮影とOCR・送信は別スレッド。OCRや通信待ちは次の撮影を妨げない。
二重起動はOSのファイルロックで防ぐ。異常終了後はOSがロックを解放する。

## 撮影と操作

- 起動後、設定済みなら直ちに撮影し、以後30秒ごとに撮影する。未設定なら停止状態で設定画面を開く。
- 接続中の全画面を毎回列挙し、1画面につき1記録を保存する。負の座標を持つ副画面も対象。
- 同じ周期の各画面に同一の `capture_id` とUTC時刻を付ける。画面識別にはWindowsのディスプレイ名を使う。
- `photo_id` は撮影ごとに生成するUUID由来のID。内容が同一でも前回とは別ID。再送だけ同一IDを使う。
- ロック中・セキュアデスクトップ・取得失敗時は状態を表示し、次の周期で再試行する。
  スリープ中の画面は取得できないため、復帰後は過去分を捏造せず現在の画面から再開する。
- 一時停止は新規撮影と次のOCR・送信を止める。既に開始した撮影・通信は完了する場合がある。
- ウィンドウを閉じても常駐を続ける。トレイまたは設定画面の「終了」で終了する。
- サインイン時の自動起動は設定画面で切り替える。初期値は無効。

## OCR・画像

OCRには縮小前のPNGを渡し、`ja` を明示する。OCR結果は改行を保って保存する。
エンジンの最大寸法を超える画面は原寸のタイルに分ける。タイル境界の文字には認識欠落の可能性がある。
OCR後、同じ画素数のJPEG（品質90・色差間引きなし）を作り、クラウドへ送る。
ローカルのPNGはOCRとJPEGの保存がコミットされた後に解放する。

OCR失敗・日本語OCR未導入・タイムアウトの場合、元PNGを残して再試行し、状態画面に失敗を表示する。
OCR本文は最大128KiB、multipart全体は最大20MiB。超過時も無言で切り捨てず、未送信キューに保持する。

## 永続キューと認証

保存先は `%LOCALAPPDATA%\LifelogScreenshot`。

- `outbox.sqlite3` に画像・時刻・画面情報・OCR・試行回数を保存。WALを使い、撮影時点でコミットする。
- 再起動後も未送信分を再開する。エラー時は5秒から最大1時間まで指数バックオフし、後続の記録は送信できる。
- サーバの2xxに加え、応答の `photo_id` 一致と `source=desktop` を確認してからローカル行を削除する。
- SQLiteファイルの空きページは再利用するため、送信後にファイルサイズが直ちに縮むとは限らない。
- 認証にはCloudflare Accessのサービス資格情報とPC専用の `DESKTOP_TOKEN` を使う。管理者トークンは不要。
  PC専用トークンは `source=desktop` の写真PUTだけを許可し、検索・管理API・MCPは許可しない。
  既存のR1取り込みトークンによる送信との互換性も維持する。
- 認証情報はWindows DPAPIで現在のユーザーにひもづけて暗号化し、`config.json` に保存する。
- HTTPS必須。ただしローカル検証用のlocalhostだけHTTPを許可する。リダイレクトには追従しない。
- ログは1MiB×最大4ファイル。OCR本文・画像・資格情報・レスポンス本文をログに出さない。

## APIと保存スキーマ

既存の `PUT /v1/photos/{photo_id}` を拡張する。R1・眼鏡の生JPEG送信は維持する。

PCの場合はクエリに `source=desktop`、`taken_at`、`device_id`、JPEGの `sha256` を付け、
`multipart/form-data` で次を送る。

| パート | 内容 |
| --- | --- |
| `image` | 原寸JPEG、`image/jpeg` |
| `metadata` | JSON文字列。`capture_id`（32桁hex）、`monitor_id`、`width`、`height`、`ocr_text` |

migration `0019_desktop_screenshots.sql` で `photos` に上記の5列を追加する。
画像は既存のR2へ、行はD1へ保存し、既存キューで `captionPhoto` を呼ぶ。
PC用プロンプトはアプリ・作業・図の要約を求め、OCRの全文転記や画面内の指示への追従を求めない。

PC画像の重複リクエストで既存行が `pending` の場合は再度キューに入れる。
D1保存後・キュー投入前の失敗で、クライアントの再送が未処理画像を置き去りにしないため。

送信前に `/health` の `desktop_upload: 1` を確認する。旧Workerは未知のsourceをR1に落とすため、
確認に失敗した場合は画像本体を送らず、サーバ更新を待って再試行する。

## 検索・コンテキスト・表示

`photos_fts` を `caption` と `ocr_text` の2列を索引するtrigramテーブルへ移行する。
既存キャプションも全件再投入する。INSERT・UPDATE・DELETEトリガで同期し、空文字・NULLへの訂正も索引から除く。

- 3文字以上はFTS、2文字以下は両列のLIKE検索。
- PCのOCRが非空なら、キャプションが未生成または失敗でも検索・コンテキストに含める。
  R1・眼鏡は従来どおり `status=captioned` かつ非空キャプションを必要とする。
- 検索結果の `kind=photo` は維持し、`source=desktop` を追加。`text` はキャプションとOCRを改行で連結する。
- `contextData.text` は音声のみのまま。`seen` にPCのキャプション・OCRを含め、
  `photos` には `ocr_text`・`capture_id`・`monitor_id` を付ける。
- 日ビューでは `capture_id` ごとに各画面をまとめる。同じ分の別周期を混ぜない。
  「PC · 画面名」を表示し、OCR本文は折り畳みで読めるようにする。
  UTCと時差付きの時刻を `Date.parse` で同じ時間軸に変換してから古い順に並べる。
  Web画面は自動更新せず、再読み込みで最新の記録を取得する。
- MCPのツール名・引数は維持し、説明にPCの出所とOCRを明記する。

## 容量と保持

2画面・30秒間隔では8時間で1,920画像、24時間で5,760画像。
同じ画面も別時刻の記録として保存・索引する。クラウドの画像・OCR・索引に自動削除や期限切れを設けない。
過去データを索引から外す最適化も導入しない。

未送信キューは自動破棄しない。ローカル空き容量が512MiB未満なら撮影失敗として状態を表示し、
容量が回復した次の周期で再開する。これは画面変化による省略ではなく、書き込み不能を避けるための扱い。
長期運用のD1容量・クラウド費用・送信速度は実測して判断する。今回は保存量を減らす方針へ変更しない。

既存の上限（検索最大100件、コンテキストの写真200件、日ビュー写真2,000件）は維持する。
2画面30秒間隔では写真200件は約50分で埋まる。日ビューは古い順に2,000件を取得するため、
上限を超えると最新分は日ビューに含まれない。APIは `photos_truncated` を返すが、
Web画面での警告表示とページングは未実装。保存・索引自体は続く。
