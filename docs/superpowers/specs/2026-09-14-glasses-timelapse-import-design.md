# 眼鏡カメラのタイムラプスを Web 画面から取り込む

作成日: 2026-09-14 (JST)
対象: `cloudflare/lifelog`
ブランチ: `main` から分岐予定

## なぜやるか

時折、眼鏡にアタッチするカメラを使う。30秒間隔のタイムラプスで撮れるが、
出てくるのは `.mov` が1本で、いまのアーカイブには入れる経路がない。

USB でつないだあと、Web 画面からフォルダを選んで取り込めるようにする。

**目的は保存ではなく、自分が何を見ていたかのコーパスを作ること。**
いま必要なわけではないが、後から必要になったときに遡れない。
記録は溜め始めないと取り戻せないので、読み出し側より先に作る。

この位置づけの違いは設計に効く。保存が目的ならフレームは画像でよいが、
コーパスが目的なら**成果物はキャプションのテキスト**で、画像はその原本になる。
解像度もプロンプトも、そちらを向いて決める。

## この設計だけでは完結しない

`photos.caption` を読んでいる箇所を全部洗ったところ、3つしかなかった。

| 読んでいる場所 | 用途 |
| --- | --- |
| `src/index.ts:701,742` `dayView` | 日ビューに表示する |
| `src/ui.ts:158` | 同上 |
| `src/index.ts:1307` `captionBackfill` | 未キャプションの行を探す |

`searchData`（`/v1/search`）も `contextData`（`/v1/context`）も `segments` しか見ていない。
MCP の `lifelog_search` / `lifelog_recent` はその2つを呼ぶだけなので、
**写真のキャプションは検索にもエージェントにも届かない。**
R1 のタイムラプスのキャプションも、いまは日ビューを開いた人間の目にしか触れていない。

つまりこの設計を実装しただけでは、読まれないデータが増える。
コーパスとして引けるようにするのは第2弾
（`2026-09-14-caption-corpus-design.md`）の仕事で、
**片方だけ実装しても目的は達成されない。**

第1弾を先にやるのは、記録が溜まり始めるのが先でないと後から取り戻せないから。
読み出し側は後から足しても既存の行に遡って効く。

## 決めたこと

| 項目 | 決定 |
| --- | --- |
| 位置づけ | 第1弾（取り込み）。コーパス化は第2弾に分ける |
| 取り込み単位 | 動画のまま保存せず、**ブラウザでフレームに分解して既存の `photos` に流す** |
| 分解の場所 | クライアント。Workers に ffmpeg は無く、WASM は CPU 上限に当たる |
| ファイル選択 | `<input type="file" webkitdirectory>`。USB 挿入の自動検知はできない |
| 画面 | 既存 UI のタブではなく `/import` として独立させる |
| 音声トラック | 捨てる。1.5秒しか入っておらず文字起こしの対象にならない |
| 開始時刻 | `file.lastModified` から逆算し、画面で修正できるようにする |
| 撮影間隔 | 画面で指定。既定30秒、`localStorage` に保存 |
| 解像度 | 1920×1080 のまま上げる。視線の先の文字を読ませるため |
| キャプション | 全フレームに付ける。**これが成果物**。眼鏡カメラ専用のプロンプトを別に持つ |
| 重複排除 | `photo_id` を元ファイルのハッシュから決める。再取り込みは安全 |
| 時刻の訂正 | 管理エンドポイントで、取り込み単位で `taken_at` を引き直せるようにする |
| アップロード | 単発 PUT。マルチパートは不要 |

| 解像度 | 1920×1080 progressive, yuv420p |
| フレーム数 | 37 |
| 再生時間 | 1.473 秒 |

### 密度

| | 1時間あたり | キャプション費用 | キュー処理 |
| --- | --- | --- | --- |
| R1（5分間隔・前後2枚） | 24枚 | 約 $0.005 | 2分 |
| 眼鏡（30秒間隔） | 120枚 | 約 $0.024 | 10分 |

単価は `migrations/0011_photo_captions.sql` に記録された実測値（640×480 で1枚 $0.0002 / 5秒）。
1920×1080 は画素数が 6.75 倍なので入力トークンも増え、実際はこの数倍になる。
それでも18分の取り込み1回で $0.03 程度。

縮小しないのは R2 が安いからではない。**頭部カメラの価値は視線の先にある文字**で、
見ていた画面・看板・書類が読めるかどうかがコーパスの質を決める。
640×480 に落とすとそこが潰れる。R1 の周囲を写すタイムラプスとは要求が違う。

### 時刻

これが一番効いた。カメラの時計まわりに2種類の時刻がある。

| ファイル | ファイル作成日時 | ファイル更新日時 | MOV の `creation_time` |
| --- | --- | --- | --- |
| MOVI0004 | 19:59:00 | 19:59:02 | `2026-09-14T11:59:00Z` |
| MOVI0006 | 20:00:52 | 20:19:02 | `2026-09-14T12:00:52Z` |

`creation_time` はファイル作成日時ちょうど **−8時間**。秒まで一致する。
カメラは JST でファイルシステムに書き、MOV のほうは UTC+8 として換算している。
つまり両者は同じ情報で、どちらも**録画開始時刻**を指す。

更新日時は録画終了。MOVI0006 で検算すると合う。

```
20:00:52 + 36区間 × 30秒 = 20:18:52
ファイル書き終わりの10秒後が 20:19:02
```

**問題は、ブラウザがファイル作成日時を読めないこと。**
File API が渡すのは `lastModified`（＝更新日時＝録画終了）だけで、
作成日時に相当するものは仕様に無い。
加えて作成日時はファイルをコピーすると書き換わるので、そもそも当てにできない。

`creation_time` に +8時間する案は却下した。いまは秒まで合うが、
カメラのタイムゾーン設定を直した瞬間に8時間ずれた記録が静かに入り始める。
腐ることが見えているマジックナンバーは置かない。

採用するのは更新日時からの逆算。

```
開始時刻 = lastModified − (フレーム数 − 1) × 間隔
N番目の時刻 = 開始時刻 + N × 間隔
```

MOVI0006 で 20:19:02 − 18:00 = 20:01:02。実際の 20:00:52 と10秒ずれるが、
30秒間隔のタイムラプスでは誤差のうち。
それでも合わないときのために、画面で開始時刻を直接編集できるようにする。

## サーバ側 — `cloudflare/lifelog`

### マイグレーション `migrations/0017_photo_source.sql`

```sql
-- どの機材から来たフレームか。
--
-- 眼鏡カメラのタイムラプスは30秒間隔で、R1 の5分間隔の10倍の密度がある。
-- 同じテーブルに入れる（写真であることに変わりはなく、キャプションも日ビューも
-- 配信も共通）が、日ビューの見せ方だけは分ける必要があるため出所を持つ。
ALTER TABLE photos ADD COLUMN source TEXT NOT NULL DEFAULT 'r1';

-- 取り込み元の動画1本を指す識別子。眼鏡カメラのフレームにだけ入る。
--
-- 日ビューで「この18分ぶん」を1エントリにまとめるため、および時刻を後から
-- 引き直すときの単位として使う。R1 の写真は NULL。
ALTER TABLE photos ADD COLUMN source_file TEXT;

CREATE INDEX IF NOT EXISTS photos_source_file ON photos(source_file);
```

### `photo_id` の決め方

再取り込みしても増えないことが要る。`putPhoto` は既存 id を
`duplicate: true` で弾く（`src/index.ts:1141`）ので、id が決定的なら重複排除はただで手に入る。

```
photo_id = "g" + <元ファイル SHA-256 の先頭16桁hex> + "-" + <フレーム番号4桁0詰め>
例: g3f8a1c9e04b27d6f-0012
```

22文字で、既存の検証 `/^[A-Za-z0-9_-]{8,64}$/` を通る。

ファイル名は使わない。カメラは `MOVI0006.mov` を SD カードを消すたびに再利用するため、
名前では別の日の別の記録と衝突する。内容のハッシュなら衝突しない。

`crypto.subtle.digest('SHA-256', arrayBuffer)` で取る。2.5 MB なら一瞬。

### `putPhoto` に足すもの

`src/index.ts:1126`。クエリパラメータを2つ受ける。

| パラメータ | 値 | 既定 |
| --- | --- | --- |
| `source` | `r1` \| `glasses` | `r1` |
| `source_file` | 16桁hex、`source=glasses` のとき必須 | なし |

R2 のキーは `photo/YYYY/MM/DD/<photo_id>.jpg` のままでよい。
`photo_id` の先頭が `g` なので、キーを見れば出所は分かる。

`INSERT` に2列足すだけで、それ以外の流れ（R2 put → D1 insert → キュー送信）は変えない。
キャプションのキューも既存のまま通す。

### キャプションのプロンプトを分ける

既存の `CAPTION_PROMPT`（`src/index.ts`）は R1 の 640×480 に合わせて書かれている。

```
この写真に写っているものを日本語で簡潔に説明してください。
人物の有無、場所の様子、目立つ物を2〜3文で。推測は避け、見えるものだけを述べてください。
```

R1 は装着者の周囲を写す。眼鏡カメラは**装着者が見ていたもの**を写す。
同じプロンプトを当てると、後者でも「場所の様子」が返ってきて、
肝心の「何を見ていたか」が落ちる。

`captionPhoto` が `photos.source` を読んで選ぶ形にする。

```typescript
const CAPTION_PROMPT_GLASSES =
  "これは頭に装着したカメラの映像で、撮影者が見ていたものです。" +
  "何を見ていたかを日本語で2〜3文で説明してください。" +
  "画面・書類・看板などの文字が読める場合はその内容を含めてください。" +
  "推測は避け、見えるものだけを述べてください。";
```

文字を拾わせるのは、1920×1080 のまま上げる判断と対になっている。
解像度を保つ理由がここにあり、プロンプトで指示しなければ活きない。

`CAPTION_MAX_TOKENS` は 220 のまま。文字を読ませるぶん長くなりうるが、
上限の理由（長いキャプションは誰も求めていない）は変わらない。
足りなければ実物を見てから上げる。

### `dayView` のグループ化を直す

`src/index.ts` の日ビューは写真を**分単位**でまとめている。
R1 が前後2枚を同じ分に撮るので、それを1組にするための処理。

```typescript
const minute = Math.floor(row.taken_epoch / 60);
```

30秒間隔のフレームはこれに素直にぶつかる。**1分に2枚入るので、
無関係な2フレームが「前後の対」として組まれてしまう。**

分け方を変える。

| 出所 | まとめ方 |
| --- | --- |
| `source = 'r1'` | いままでどおり分単位 |
| `source = 'glasses'` | `source_file` 単位。取り込んだ動画1本が1エントリ |

18分37枚が日ビューに37行並ぶのは読めないので、
1エントリの中にサムネイルを並べる形にする。

`LIMIT 1000` は 2000 に上げる。R1 だけなら1日最大576枚で余裕があったが、
3時間装着すると眼鏡側が360枚足されて上限に近づく。

### `/v1/admin/photo-retime`（新規）

開始時刻を間違えて取り込んだときの訂正。

```
POST /v1/admin/photo-retime?source_file=<16hex>&start=<ISO8601>&interval_sec=30
```

その `source_file` のフレームを `photo_id` の末尾4桁順に並べ、
`taken_at` と `taken_epoch` を引き直す。

これが無いと詰む。`photo_id` は時刻を含まないので、時刻を直して再取り込みしても
`duplicate: true` で弾かれ、古い時刻のまま残る。
逆に id に時刻を含めると、訂正のたびに重複が増える。訂正は別口で持つのが正しい。

## クライアント側 — `src/import.ts`（新規）

`src/ui.ts` には足さない。理由は2つある。

`ui.ts` は399行の1枚もののテンプレート文字列で、
動画デコードと canvas の処理を入れると読めなくなる。
それに、毎日開く閲覧画面に、時折しか使わない重い処理を載せる意味がない。
地図を遅延ロードにしているのと同じ判断（`src/ui.ts:234`）。

### 画面の流れ

```
[フォルダを選ぶ]  ← <input type="file" webkitdirectory>
        ↓
 .mov だけ拾って一覧に出す
        ↓
 各ファイルについて:
   SHA-256 を計算 → source_file
   <video> に読ませて duration と fps を得る
   フレーム数 = round(duration × fps)
   開始時刻 = lastModified − (フレーム数−1) × 間隔
        ↓
 一覧に「ファイル名 / フレーム数 / 開始時刻(編集可) / 間隔」を表示
        ↓
      [取り込む]
        ↓
 フレームを1枚ずつ canvas に描いて JPEG 化 → PUT
 進捗と、duplicate で飛ばした数を出す
```

### フレームの取り出し

```javascript
// fps は duration からは出ないので、rVFC を2回呼んで mediaTime の差から取る。
// Firefox は 132 から requestVideoFrameCallback に対応している。
const fps = await measureFps(video);          // 取れなければ 25 にフォールバック
const count = Math.round(video.duration * fps);

for (let i = 0; i < count; i++) {
  // フレームの境目を踏まないよう中央を狙う
  video.currentTime = (i + 0.5) / fps;
  await once(video, 'seeked');
  ctx.drawImage(video, 0, 0, 1920, 1080);
  const blob = await new Promise((r) => canvas.toBlob(r, 'image/jpeg', 0.85));
  await upload(blob, i);
}
```

品質 0.85 で1枚70 KB前後。ffmpeg の `-q:v 3` で抜いたとき 67〜79 KB だったので、
だいたい同じ水準になる。

### アップロード

```
PUT /v1/photos/<photo_id>
  ?taken_at=<ISO8601>
  &device_id=glasses
  &facing=rear
  &source=glasses
  &source_file=<16hex>
```

`facing` は `rear`。R1 の定義では `front` が装着者を向く0°、`rear` が外向き180°で、
眼鏡カメラは外向きなので `rear` が正しい。
日ビューのグループ化は `source` で分けるので、R1 の `rear` と混ざることはない。

同時実行は3本。37枚で37リクエストになるが、1枚70 KB なので待ち時間は問題にならない。
順番は `photo_id` が持っているので、並列で投げても復元できる。

## 失敗の見え方

| 何が | どうなる | どうする |
| --- | --- | --- |
| ブラウザがデコードできない `.mov` | そのファイルだけ「読めません」と出す | 他のファイルの取り込みは続行 |
| fps が測れない | 25 fps を仮定して続行 | 画面に「fps を仮定した」と出す |
| アップロード途中で失敗 | 成功したぶんは残る | 再実行すると `duplicate` で飛ばして続きから |
| 開始時刻が違った | フレームが違う時刻に並ぶ | `/v1/admin/photo-retime` で引き直す |
| フレーム数の読み違い | 末尾が欠けるか、空フレームが出る | `currentTime > duration` で打ち切る |

途中で失敗しても壊れないのは、`photo_id` が決定的だから。
R2 に入ったバイトは消さず、やり直しは常に足りない分だけを埋める。

## テスト

いま `cloudflare/lifelog` にテストが無いので、`vitest` を入れる。
`cloudflare/reader` に入れたときと同じ形。

純粋関数として切り出して単体テストを書く対象は2つ。

| 関数 | 置き場所 | テストすること |
| --- | --- | --- |
| `frameTimes(lastModified, count, intervalSec)` | `src/import-time.ts` | 逆算が合うか。境界: 1フレーム、日またぎ、間隔変更 |
| `photoIdFor(fileHash, index)` | `src/import-id.ts` | 4桁0詰め、長さ、既存の正規表現を通ること |

MOVI0006 の実測値（`lastModified` 20:19:02 / 37枚 / 30秒 → 開始 20:01:02）を
そのままテストケースにする。

フレーム抽出と canvas はブラウザ API なので単体テストの対象にしない。
実機（Firefox Nightly）で `MOVI0006.mov` を取り込み、
37枚が20:01〜20:19に並ぶことを目視で確認する。スクリーンショットを残す。

## やらないこと

| やらないこと | 理由 |
| --- | --- |
| `.mov` をそのまま保存して再生 | 18分の記録が1.5秒のクリップになり、後から探せない |
| サーバ側でのフレーム分解 | Workers に ffmpeg が無い。WASM は CPU 上限 |
| USB 挿入の自動検知 | ブラウザにその API は無い。セキュリティ境界なので回避しない |
| File System Access API | Chromium 専用。Firefox で動かない |
| 音声トラックの文字起こし | 1.5秒しか入っていない |
| 同じ SD カードの `PICT*.jpg` と `RECR*.wav` の取り込み | 今回の依頼は動画。別途判断する |
| フレームの間引き | 30秒間隔は既にカメラ側で間引かれた結果。これ以上落とす理由がない |
| 画像の縮小 | R2 の egress は無料で、1日使っても67 MB。残すほうを取る |

## 残っていること

同じ SD カードに `PICT*.jpg`（静止画、600 KB前後）と `RECR*.wav`（音声、16 kHz）が入っていた。
どちらも既存のテーブルにそのまま乗る形をしている。
`RECR*.wav` は `segments` に入れれば Whisper に通る。
ただし今回の依頼は動画なので、やるかどうかは別に決める。

**第2弾（`2026-09-14-caption-corpus-design.md`）をやらないとこの設計は目的を果たさない。**
取り込んだキャプションは検索にもエージェントにも届かないままになる。
実装中にここを見失わないよう、BACKLOG.md の Agreed にも項目を立ててある。

連続するフレームはほとんど同じ絵なので、似たキャプションが並ぶ可能性はある。
以前は「役に立たなければ間引く」と書いていたが、その保留は取り下げる。
キャプションが成果物である以上、減らす方向の判断ではなく、
