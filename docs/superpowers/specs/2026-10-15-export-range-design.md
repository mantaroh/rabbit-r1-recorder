# 時間帯を指定した音声・文字起こしのダウンロード

2026-10-15 JST

## 決めたこと

- 日ビューに「ダウンロード」ボタンを付ける。その日の開始〜終了時刻を選んで、音声を ZIP、文字起こしをテキストで落とせる。
- 先に「件数を確認」で件数と大きさを出してから、ダウンロードのボタンが押せるようになる。
- 音声は1セグメント1ファイルのまま ZIP に入れる。ZIP には `transcript.txt` も入れる。
- admin だけ（ブラウザは Cloudflare Access 経由で admin）。端末・PC・エージェントの資格情報では落とせない。

## API

| メソッド | パス | 返すもの |
| --- | --- | --- |
| GET | `/v1/export/audio?from=&to=[&dry_run=1]` | ZIP。`20261015_093000_<segment_id>.wav` と `transcript.txt`。dry_run は `{segments, bytes, transcripts, max_bytes}` |
| GET | `/v1/export/transcript?from=&to=` | `text/plain`。1行1セグメントで `2026-10-15 09:30:00  本文` |

- 時間帯は [from, to)、24時間まで。削除と同じ `parseRange` を使う。
- 対象は `kind='lifelog'` だけ。日ビューに出ない呼びかけ（`query`）は入れない。
- 文字起こしは日ビューと同じ基準（`segmentText`）。定型句・空・未処理は入れない。
- ファイル名は `lifelog-20261015_0900-1000.zip` / `.txt`。時刻はすべて JST。

## ZIP の作り方

- 無圧縮。WAV も Opus も縮まないので、圧縮しても CPU の無駄になる。
- R2 から読みながら流す（`ReadableStream` の pull）。全体をメモリに載せない。
- CRC は流したあとでないと分からないので、各ファイルの後ろに data descriptor を置く。
- ZIP64 は使わない。合計（`segments.bytes` の合計）が 2GB を超えたら 413 で断る。WAV 48kHz で6時間弱。
- R2 に実体がない行は飛ばす。

CRC32 は最初1バイトずつの表引きで書いたが、256MB に約2.9秒かかった。2GB だと約23秒で、Worker の CPU 上限（既定30秒）に近い。slicing-by-8 に変えて約0.37秒（2GB で約3秒）。結果は Node の `zlib.crc32` と一致。

## 却下した案

| 案 | 理由 |
| --- | --- |
| 1本の WAV に連結 | 録音の切れ目が詰まって時刻が分からなくなる。Opus やサンプルレート違いが混ざると作れない |
| ブラウザ側で ZIP | 全部メモリに載る。CDN のライブラリが要る |
| R2 に ZIP を作って置く | 保存と後片付けが増える |

## 影響

- 読み取りだけ。D1 のマイグレーションなし。R1・PC 側の変更なし。
- 削除した時間帯は行がないので出てこない。
- 24時間を超えたときのメッセージを「一度に消せるのは〜」から「一度に指定できるのは24時間までです」に変えた（削除と共用のため）。

## 確認したこと

- 単体テスト 111件通過（`test/export.test.ts` を追加。ZIP を読み戻して CRC・data descriptor・日時を照合）。
- ローカル Worker（`wrangler.desktop-test.jsonc`、ポート 8791）に WAV を3件上げ、1件を定型句にして確認。
  - dry_run: 音声3件・文字起こし2件。
  - ZIP: `unzip -t` でエラーなし。中身は WAV 3つと `transcript.txt`。
  - テキスト: 定型句の行が入らないこと。
  - 端末の資格情報は 403、24時間超は 400。
- 画面: ダイアログで件数を確認し、2つのボタンで ZIP とテキストが落ちることを Playwright（Chromium）で確認。Firefox Nightly では未確認。
- `tsc --noEmit` は `src/index.ts:299`（キューのハンドラの型）だけエラー。今回の変更とは関係ない箇所。
